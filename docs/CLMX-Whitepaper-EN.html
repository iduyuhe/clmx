01Abstract

CLMX is a vertical AI model training, inference & capability-open platform for the industrial internet. It abstracts the workshop-style task of "training one anomaly-detection model for one device" into a reusable, orchestratable, and externally openable model factory.

CLMX uses industrial equipment predictive maintenance (PdM) as its first landing shell, yet its base is a general model production & operation system: it ships two training-inference-isomorphic engines — unsupervised time-series anomaly detection and a zero-dependency Chinese text classifier — and, toward the goal of making the platform itself somewhat intelligent, delivers a half-agent closed loop (natural-language interaction → auto baseline → automated anomaly handling → automated training interpretation).

On the ingest side, CLMX introduces an AI-native ingest generator: it extracts measurement points from device docs/samples/descriptions, generates a thing model and a zero-dependency collector driver, and self-tests it in place. On the open side, CLMX exposes its APIs as 10 standard tools over a northbound MCP (Model Context Protocol) capability base, enabling external AI agents to orchestrate CLMX directly. Together these two directions defend the moat — training-inference isomorphism + zero-dependency edge JS inference — so models run at the edge without any deep-learning framework.

This white paper presents CLMX's positioning, architecture, four core capabilities, ML pipeline, key technical decisions, security model, and open-source roadmap for technical decision-makers, integrators, and contributors.

02Background & Industry Challenges

2.1 Pain points of industrial predictive maintenance

Unplanned downtime of industrial equipment is extremely costly. Traditional "scheduled maintenance" either over-services or misses failures. Data-driven PdM is the公认 direction, yet landing it has long been stuck behind four hurdles:

🧩

Integration hell

Brands, protocols, and point namings vary wildly. Every new device needs a bespoke collector driver and thing model — high effort, error-prone, hard to reuse.

🏷️

Scarce labels

Anomaly samples are rare and expensive. Supervised learning starves on the factory floor before training even begins.

🖥️

Edge can't run it

Deep-learning frameworks are heavy and dependency-laden, hard to deploy on gateways/edge nodes; pushing all inference back to the center adds latency and bandwidth cost.

🧱

Platform not smart

Most tools are just "dashboards + threshold alerts". A human still has to understand, handle, and review every alert — the platform itself is absent from the decision loop.

2.2 Three shortcomings of existing solutions

  • Biased toward "a single model" rather than "a model production system": most PdM offerings deliver one trained model, lacking the ability to productize, repeat, and operate the modeling process.
  • Biased toward "bolting on a chatbot" rather than "opening capabilities": equating AI with a chat entry point, without exposing platform capabilities via a standard protocol that external agents can orchestrate.
  • Center-heavy, edge-light: inference depends on central GPUs/frameworks, leaving the edge as mere passthrough and forfeiting "near-edge intelligence" elasticity.
CLMX's design starting point is not "a smarter dashboard", but engineering away all four hurdles at once: auto-generated ingestion, label-free training, zero-dependency inference, and a semi-autonomous platform.

03Positioning & Design Philosophy

3.1 What CLMX is: a model factory, not a single model

One frequently confused concept needs clarifying:

ConceptDefinitionCLMX's role
Vertical modelA specific model trained for one scenario (e.g. air-compressor vibration anomaly detection)What CLMX produces
AgentAn autonomous role that calls models to complete tasksCLMX's consumer / orchestrator
CLMXModel factory + inference service + capability-open platformThe base that trains, hosts, and opens models

External tagline: "A vertical AI model training & inference platform for the industrial internet". The platform produces vertical models; agents call them — the two are bridged by northbound MCP.

3.2 Core design principles

Zero-dependency first

Implement training and inference in pure JS / stdlib wherever possible, avoiding heavy frameworks so the edge can run and dependencies stay controllable.

Train-infer isomorphism

Training and inference share the same code and numeric logic, eliminating the "train in Python, ship in another stack" drift and maintenance cost.

Multi-tenant isolation

Row-level data isolation; every CRUD forcibly carries tenantId; delivered as a platform-as-a-service (SaaS).

3.3 HubPort idea fusion

CLMX evaluated the ideas of "HubPort (an AI-native IoT platform)" and concluded: fuse the ideas, not the product. It adopts four core ideas and is explicit about what it does not copy:

IdeaAdoption (in CLMX)
T1 · AI-native ingestIngest generator: doc/description → auto thing model + collector driver + self-test
T2 · AI at create, zero-AI at runtimeDriver generated by AI/heuristics at create time, executed as pure zero-dep JS at runtime (same moat)
T3 · Capability assetizationIngestSpec / IngestAsset models + publish marketplace + one-click reuse (reuseCount)
T4 · Northbound opennessSelf-implemented MCP base wrapping platform APIs into 10 standard tools for external agents
Red line: "AI-native ≠ bolting on a chatbot". CLMX does not copy HubPort's product breadth (680+ features / full-stack IoT), multi-language runtime (keeps zero-dep JS), or controlled CLI shell access (chooses the MCP standard instead).

04Overall Architecture

CLMX uses a clean front-end/back-end separated, layered service architecture. The back end serves via Express + Prisma; the front end is React + TypeScript + Tailwind. The ingest layer supports both MQTT (aedes) and the AI-native ingest endpoint; the model layer uses a Python worker (CPU mode) for training, while inference sinks to zero-dependency JS.

05Capability 1: Half-Agent Closed Loop

CLMX targets its own intelligence maturity at stage 3, the "half-agent": a perceive-decide-act closed loop, but not a fully autonomous agent (which would conflict with the zero-dep edge base). Four capabilities cooperate into a loop:

Figure 2 · Half-agent loop: NL entry → auto baseline → anomaly handling (core) → training interpretation

① Natural-language interaction entry

Upgrades "dashboard operations" to "language operations". Users describe intent in Chinese (e.g. "generate last week's health score for cooling pump #1"); the platform parses and invokes the corresponding capability. This entry is also exposed northbound as clmx_nl_command for external agents.

② Auto baseline & health score

The platform auto-computes baselines and health scores per point from history; alert thresholds are no longer hand-guessed. When health < 60, Notification + AlertChannel auto-push, no manual watching needed.

③ Automated anomaly handling loop (core)

On detecting an anomaly, the platform can auto-trigger an action chain (notify, dispatch, linkage, and if needed re-training), forming a "perceive-decide-act" loop. This is what separates CLMX from "dashboard + threshold".

④ Automated training interpretation

After training/inference, the platform auto-produces a readable interpretation (metrics, anomaly intervals, suggestions), lowering the barrier and making the loop explainable and auditable.

The half-agent does not pursue "full autonomy". It runs the loop within human-set boundaries — handing repetitive, programmable decisions to the platform while leaving value judgments to users. That is exactly the controllable intelligence industrial scenarios need.

06Capability 2: AI-Native Ingest Generator

6.1 Pain point: integration hell

On the factory floor, every new device needs a hand-written collector driver, a thing model, and point-name alignment. CLMX's ingest generator automates this:

Figure 3 · Ingest generator pipeline: from unstructured input to runnable, reusable asset

6.2 Point-extraction priority

The generator tries in descending confidence, stopping at first hit:

  1. Structured JSON: parse point definitions directly;
  2. Sample inference: reverse-infer point types/units from collected samples;
  3. Heuristic dictionary from description: extract via a Chinese industrial lexicon ("temperature/pressure/vibration/rpm/current");
  4. Optional LLM (env-gated): used only when an LLM key is configured; no npm dependency, pure HTTP call.

6.3 Thing model & zero-dependency driver

After extracting points, a standard thing model and a zero-dependency JS collector driver collect(ctx) are generated. The driver is generated by AI/heuristics at create time and runs as pure JS at runtime — exactly HubPort T2: AI at create, zero-AI at runtime.

6.4 Sandbox self-test & runtime

After generation, the driver is executed in a new Function sandbox to verify it yields finite numeric values; once passed it can be published to the asset marketplace. The runtime endpoint receives the driver and executes it, writing results to SensorData, coexisting with the MQTT telemetry endpoint under /api/ingest.

Snippet: generated collector driver

// produced by the ingest generator (zero-dep, pure JS at runtime)
function collect(ctx) {
  const t = Date.now();
  return [
    { point: 'temperature', value: sim(ctx, 'temperature', 65, 8), ts: t },
    { point: 'vibration',  value: sim(ctx, 'vibration',  2.3, 0.6), ts: t },
    { point: 'current',    value: sim(ctx, 'current',   12, 1.5), ts: t }
  ];
}
Assetization: results are persisted as IngestSpec (requirement draft) / IngestAsset (version chain, unique(specId, version), with published, reuseCount, driverCode, thingModel). A one-click apply auto-creates sensors for a device and puts it into operation.

07Capability 3: Northbound MCP Capability Exposure

7.1 Why MCP

The platform's real value lies in "being used". CLMX chooses MCP (Model Context Protocol) as the northbound open standard instead of a self-built CLI shell — external AI agents can orchestrate CLMX capabilities directly, upgrading the platform from "clicked" to "orchestrated".

7.2 Zero-dependency JSON-RPC implementation

The MCP service self-implements JSON-RPC 2.0 over NDJSON (no official SDK), stdio transport, logs to stderr to avoid polluting the protocol stream. Auth supports CLMX_API_TOKEN passthrough or CLMX_API_EMAIL/PASSWORD auto-login. Exit logic waits for in-flight requests after stdin closes, so no request is dropped.

08Capability 4: Multi-tenant SaaS Foundation

CLMX is delivered as a service; all data is isolated per tenant.

Row-level isolation (an inviolable constraint)

  • Every CRUD where must include tenantId: req.tenantId;
  • When operating sub-resources, the parent is first queried to verify ownership, preventing escalation;
  • req.tenantId / req.userRole are injected from the JWT by authMiddleware;
  • Preset data uses tenantId: null; queries use OR [tenantId=?, tenantId=null] for compatibility.

Value-added capabilities

Since stage 4, quota, billing, and white-label SaaS value-adds exist, so the platform can self-operate and also serve as a base for integrators to redistribute.

Isolation is the first line of security. CLMX makes tenantId filtering a route-layer enforced convention (not a business-code discipline), architecturally eliminating the "forgot the condition → cross-tenant leak" hazard.

09Machine Learning Pipeline

9.1 Unsupervised anomaly detection

Uses Autoencoder / Isolation Forest and other unsupervised methods to learn the distribution from normal-condition data and score deviations — label-free, directly answering the "scarce labels" reality so it can go live without anomaly samples.

9.2 Zero-dependency Chinese text classification

For Chinese text such as work orders and logs, a Naive Bayes implementation is used — train-infer isomorphic, pure JS, with no NLP framework. The keyword tool clmx_keywords exposes this capability externally.

9.3 Train-infer isomorphism & edge JS inference

Training (Python worker for heavy fitting) and inference (zero-dep JS) share the same numeric logic. The inference side introduces no deep-learning framework, so it runs directly at the edge node — "near-edge intelligence" — a core moat of CLMX.

9.4 Alert delivery

Notification + AlertChannel are live: when health < 60 it auto-pushes and can be routed per channel (e.g. WeCom, Webhook). An alert is not an endpoint but the trigger of the "half-agent loop".

12Security & Compliance

  • Auth & authorization: JWT + Bearer + RBAC (4 levels, incl. MANAGER); sensitive ops (compute health, trigger training, run inference) are role-gated.
  • Multi-tenant isolation: architectural tenantId enforced filtering (see §8).
  • Secret management: real .env and secrets never enter git history; .gitignore isolates .env / *.db / secrets / .workbuddy; deploy passwords come via env vars (e.g. CLMX_SSH_PASS), never in repo.
  • Vulnerability disclosure: SECURITY.md provides a private reporting channel to avoid premature public exposure.
  • Dependency security: dependabot.yml weekly auto-updates for front/back npm, Python, and github-actions.
Open-source security audit conclusion: no real secrets leaked in history; published files (LICENSE/README/community health files) were audited before入库.

15Conclusion

CLMX is not another "smarter dashboard". It upgrades industrial AI from "train one model" to "operate a model factory" — using an AI-native ingest generator to absorb integration cost, zero-dependency edge inference to hold the runtime boundary, northbound MCP to open capabilities to external agents, and a half-agent loop to let the platform itself participate in decisions.

We open-source the whole platform under MIT — a commitment to "industrial-internet AI for all", and an invitation to build ingest templates, model algorithms, and the asset market together. The door of the model factory is open.

How to participate: ① File Issues & PRs on GitHub/Gitee; ② Contribute device templates to the asset market via the ingest generator; ③ Build your industrial agent on the MCP tools; ④ Share your landing practice in Discussions.
