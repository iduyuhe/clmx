We Open-Sourced CLMX: Lowering the Barrier to Industrial AI

For the past six months we've been chasing one idea: letting an ordinary factory run its own industrial AI — without hiring an algorithm team, without stacking up GPUs, and without building a platform from scratch. Today we're open-sourcing that system: CLMX.

1. What is CLMX

In one sentence: CLMX is an industrial-internet-oriented platform for training, inference, and capability opening of vertical AI models.

More precisely, CLMX is not a single "smart model", nor a "chatbot". It is a model factory — feed it your equipment's operational data and it trains a predictive-maintenance model that is uniquely yours; hand it a device manual and it auto-generates a collector to pull the data in; talk to it in natural language and it evaluates health scores, runs inference, and triggers training for you.

Its three-layer positioning:

🏭 Surface · Industrial preventive maintenance
Equipment health scores, anomaly alerts, predictive maintenance — the business value users see directly.
🧠 Middle · NLP / ML model platform
Unsupervised anomaly detection, zero-dependency Chinese text classification, the model training & inference core.
☁️ Base · SaaS multi-tenant delivery
Row-level data isolation, quotas & billing, white-label — one platform serving many customers.

2. The Pain Points We Saw

Doing industrial AI, we kept hitting the same "four walls":

  • Integration is hell: thousands of device protocols and ad-hoc fields — wiring data is often harder than modeling itself.
  • Labels are scarce: industrial fault samples are rare; supervised learning frequently runs out of fuel on the shop floor.
  • Edge can't run it: deep-learning frameworks measured in gigabytes simply don't fit into on-site edge boxes.
  • Platforms aren't smart: many "platforms" just pile tools together; humans still make every call.

Nearly every design choice in CLMX was forced out of these four walls.

3. Four Core Capabilities

1Semi-Agent Closed Loop

We don't build a "fully autonomous agent" (that conflicts with our zero-dependency edge base). Instead we land at the 3rd tier — "semi-agent": natural-language commands → auto-baseline / thresholding → automatic anomaly handling → automatic training interpretation. A perception-decision-action loop, with humans guarding only the key nodes.

2AI-Native Ingestion Generator

Our answer to "integration is hell". Drop in a device manual, a sample dataset, or a one-line Chinese description — it extracts measurement points, generates a thing model, and emits a zero-dependency JavaScript collector, then self-tests it in a sandbox before delivery. A wiring tech can onboard a new device in minutes.

3Northbound MCP Capability Opening

CLMX isn't just a platform "to be used" — it's a capability "to be orchestrated". We implemented a zero-dependency JSON-RPC (MCP protocol) server exposing 10 tools — NL commands, device listing, health dashboards, trigger-training, run-inference — so external AI agents can directly schedule CLMX's capabilities.

4Multi-Tenant SaaS Isolation

Every CRUD is forced to carry tenantId row-level isolation; preset data is shared via tenantId IS NULL; JWT injects identity and role. One platform, safely serving many customers.

4. Two Moats in the Technical Base

🔧 Zero-dependency
Core inference depends on no deep-learning framework — pure JavaScript runs on edge boxes. Deployment size is measured in KB, not GB.
🔁 Train-infer isomorphism
Training and inference share the same code and math definitions, so a model leaving the platform runs on-site directly — no "trains well, can't infer" gap.
We use "unsupervised anomaly detection" to solve label scarcity, and "zero-dependency Naive-Bayes NLP" to solve edge constraints — pragmatic, but not a shortcut.
